Triage Layer — Design Notes
How triage works
When a complaint comes in, services/triage_service.py calls run_triage(text, location). This asks providers/factory.py for whichever provider is currently configured, sends it the complaint text and location, and gets back a TriageResult — a category, a priority, a one-line summary, and a confidence score. That result is what the backend stores alongside the complaint and what the frontend displays.
There are four providers behind the same interface (TriageProvider in schemas.py / providers/base.py), and the calling code never knows or cares which one it's actually talking to:
llm_provider.py — the real one. Calls Groq's API, asks for a JSON response, and validates that response against the TriageResult schema before trusting it.
ollama_provider.py — same interface, but calls a local Ollama server instead of a hosted API. Useful if a teammate's Groq key runs out or the API is down.
rule_provider.py — no AI at all. A keyword table maps words like "leak" or "pipe" to the water category, and words like "urgent" or "emergency" bump priority to high. This is deliberately dumb and deterministic — its whole job is to never fail.
simulated_provider.py — a fake used in dev and CI. It behaves like an LLM (varies its confidence score per input) without needing an API key or network call, so tests and early frontend/backend work don't depend on Groq being reachable.
Provider selection
Which one runs is controlled entirely by the TRIAGE_PROVIDER environment variable — llm, ollama, rules, or simulated. factory.py reads this variable and imports only the matching provider. In practice: CI and early local dev run with simulated, the demo/graded run uses llm, and rules or ollama exist as backups if the Groq key hits a rate limit during grading.
The reason this lives behind an env var instead of an if statement scattered through the code is that swapping providers should never mean touching triage_service.py or the routes — it's a config change, not a code change. That separation is also what makes the fallback path (below) possible without special-casing anything.
Timeout, retry, fallback
llm_provider.py sets a 10-second timeout on the Groq call. That number is a judgment call, not a measured optimum — long enough that a normal LLM response isn't cut off, short enough that a hung request doesn't leave a user staring at a spinner for a full minute.
If the call times out, triage_service.py retries once, after a short random delay (100–500ms jitter, so multiple simultaneous retries don't all hit the API at the exact same moment). Only timeout-type errors are retried — a validation error (the LLM returned malformed JSON, or a category outside the enum) is not retried, because retrying won't fix a fundamentally malformed response; it goes straight to fallback instead.
If the retry also fails, or the error wasn't retryable to begin with, RuleProvider runs instead. This is the one piece of the whole triage layer that is not allowed to fail — no network call, no external dependency, just a keyword lookup — so a complaint submission never returns an error to the user because of an AI outage. Whichever path actually produced the result is recorded in triaged_by (llm:groq, llm:ollama, rules, or rules:fallback), so it's always possible to tell after the fact whether a given complaint got a "real" AI classification or the safety net.
Caching
triage_cache.py caches the full TriageResult in Redis, keyed by a SHA-256 hash of the complaint text (lowercased and trimmed first, so trivial whitespace/casing differences still hit the same cache entry). The TTL is 24 hours — long enough that a genuinely duplicate complaint submitted later the same day doesn't cost a second LLM call, short enough that if the triage logic itself changes, stale results don't linger for weeks.
(Once you've run this locally with some repeated/near-duplicate test submissions, record the real number here: "Over N submissions, cache hit rate was X%." hit_rate() in triage_cache.py gives you that number directly.)
Known limitations
The cache key is a hash of the exact text, so two complaints that mean the same thing but are worded differently won't share a cache entry — this trades recall for simplicity.
RuleProvider's keyword table is small and can misclassify complaints that don't happen to contain one of its listed words — it's a safety net, not a substitute for the real model.
The retry logic only distinguishes "timeout" from "everything else" — it doesn't currently special-case a 429 rate-limit response differently from a genuine 5xx server error, though both are treated as retryable.
